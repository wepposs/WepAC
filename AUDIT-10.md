# WepAC — полный аудит: каталог проблем для доведения до 10/10

Проверен весь код (~7900 строк, все файлы src/, config.yml, plugin.yml, SelfTest, tools/).
Приоритеты: 🔴 критично (ложные наказания на живом сервере / мёртвые слои), 🟠 высоко, 🟡 средне, ⚪ низкое.
Формат: ГДЕ (файл:строки) → ПРОБЛЕМА → ПОСЛЕДСТВИЕ → ФИКС.

## A. Критические баги и источники ложных срабатываний (FP)

### A1 🔴 Стояние на сущностях считается «полётом» (самый массовый класс FP)
- ГДЕ: `GroundUtil.isOnGround` (GroundUtil.java:24-49) — только блоки; потребители: hover/Fly (MovementMonitor.java:136-146, 519-533), GroundSpoof (499-515), Criticals (CriticalsCheck.java:57), PacketPhysics (PacketPhysics.java:272), AirStuck (441-461).
- ПРОБЛЕМА: в ванили игрок может стоять на сущностях (другие игроки, мобы, лодка, в которой не сидит, шалкер, стойка для брони). Блочная проверка говорит «в воздухе», а клиент честно шлёт onGround=true.
- ПОСЛЕДСТВИЕ: постоять 0.8 с на голове игрока в лобби → hoverTicks>16 → флаг Fly + rollback; параллельно GroundSpoof (streak 3) → 2 РАЗНЫЕ проверки с VL → confirm-gate (2 distinct) открывается → автокик за ~10 с стояния в толпе. AirStuck добивает.
- ФИКС: в `isOnGround` при отрицательном блочном результате сканировать сущности: `world.getNearbyEntities(player.getBoundingBox().expand(0.1, 0.35, 0.1))`, искать сущность (LivingEntity/Boat/Shulker/ArmorStand/Player) чей bbox верх в пределах [feet-0.35, feet+0.08] и пересекается по горизонтали. Кэшировать результат раз в тик на игрока (используют и 20 Гц PacketPhysics, и 4 Гц монитор — см. F6).

### A2 🔴 ClientDetector, скорее всего, мёртв на 1.20.2+ (бренд переехал в configuration-фазу)
- ГДЕ: `ClientDetector.register()` (ClientDetector.java:49-51) — Bukkit-messenger на канал `minecraft:brand`; инжект netty только на PlayerJoinEvent (play-фаза, ConnectionListener.java:44-46).
- ПРОБЛЕМА: с 1.20.2 клиент шлёт бренд в CONFIGURATION-фазе; PluginMessageListener её не получает, а sniffer инжектится уже после. Цель проекта — 1.21.11.
- ПОСЛЕДСТВИЕ: весь слой детекции клиентов молча не работает; «CHEAT/SUSPICIOUS/KNOWN» вердикты никогда не ставятся.
- ФИКС: (а) на Paper — использовать `PlayerClientBrandEvent` (проверить наличие в 1.21.11) через reflection soft-hook; (б) универсально — читать `CustomPayloadPacket(minecraft:brand)` в configuration-фазе через более ранний netty-хук; (в) обязательно: самотест — если после N джойнов бренд не получен ни разу, логировать WARN «client detection INACTIVE».

### A3 🔴 Пакетная рефлексия молча умирает на Spigot-маппингах (README обещает «Spigot/Paper»)
- ГДЕ: `PacketSniffer.resolveField/readDoubleField/readFloatField` (PacketSniffer.java:200-279).
- ПРОБЛЕМА: имена `x,y,z,xRot,pitch,onGround` существуют только в Mojang-маппингах (Paper). На Spigot поля обфусцированы → fallback «уникальный примитив» неоднозначен (Pos-пакет: 3 double → отказ; Rot: 2 float → отказ) → PacketFly, pos-jump, очередь PacketPhysics и BadPackets-pitch мертвы. Предупреждение логируется только для позиции, для pitch — тихая смерть. Плюс: в 1.21.2+ структура move-пакетов менялась (дельта-кодирование) — имена полей могли съехать и на Paper.
- ФИКС: (а) объявить поддержку только Paper (проверка при включении + явная ошибка), ИЛИ (б) опциональный softdepend PacketEvents с текущей рефлексией как fallback, ИЛИ (в) таблица имён полей на версию. В любом случае: при первом джойне прогонять self-probe всех 4 полей и логировать матрицу «какие пакетные проверки активны на этом билде».

### A4 🔴 NoFall: FP-кластер «безопасных приземлений» и иммунитет отменённого урона
- ГДЕ: `MovementMonitor.trackFall` (MovementMonitor.java:754-784), `NoFallCheck` (NoFallCheck.java:21-27, `ignoreCancelled=true`).
- ПРОБЛЕМА 1 (FP): `pendingFallDamage` взводится в воздухе (проверка `softLanding` — по блоку ПОД игроком в момент взвода, там воздух). Приземление в воду (игрок встал на дно → grounded), на лестницу (схватился в падении — fall distance сбрасывается), в паутину/пухляк/сено — ваниль не наносит урона → событие не приходит → через 2 с после дедлайна флаг «landed from X blocks without damage». Падение ≥4 блоков в воду — рутинное легитимное событие.
- ПРОБЛЕМА 2 (FP): защитные плагины (WorldGuard fall-damage deny, god-режимы) отменяют событие урона; MONITOR-листенер с `ignoreCancelled=true` не срабатывает → pending не сбрасывается → флаг на КАЖДОМ падении в защищённой зоне.
- ФИКС: (1) в момент grounded-семпла проверять контекст приземления (жидкость/softLanding/climbable) и очищать pending; (2) слушать EntityDamageEvent на MONITOR БЕЗ ignoreCancelled: событие fired (даже отменённое) = легитимно, очищать pending (чит не может отменять серверные события — отмена всегда от плагина); (3) сверять `event.getDamage()` с ожидаемым `(pendingFallDistance-3)` с допуском вместо факта наличия; (4) авто-отключение проверки в мире, где N падений подряд пришли отменёнными.

### A5 🔴 X-Ray имеет путь автонаказания у статистической проверки
- ГДЕ: `XrayCheck` (XrayCheck.java:79-87, severity 5), config: `checks.xray.threshold: 10`, default-stages kick@25.
- ПРОБЛЕМА: статистика «руда/камень» имеет врождённые FP: крупные открытые пещеры, deep dark, рудоносные датапаки, просто удача. 5 флагов = VL 25 = кик (confirm-gate проходит: 25 ≥ 10×1.5). Кик по статистике недопустим.
- ФИКС: XRAY — только алерты/ручная проверка (убрать из стадий наказания по умолчанию, threshold ≥100); per-world whitelist и per-world ratio; долго: учёт «первой экспозиции» — считать только руды, не граничившие с воздухом, когда игрок впервые увидел чанк (хранить множество exposed-руд на чанк).

### A6 🔴 AirJump FP на идеальном банни-хопе
- ГДЕ: `checkAirJump` (MovementMonitor.java:682-708); `prevAirborne` сэмплируется 4 Гц (170).
- ПРОБЛЕМА: семплирование 4 Гц пропускает 1-2 тика контакта с землёй при идеальном bhop → все семплы «в воздухе», каждое окно с прыжком даёт vSpeed≈+0.25 (1.25 блока за 5 тиков разгона) при prevVSpeed≈-0.2 → условие спайка выполнено → buffer 2 → флаг через ~1 с легитимного bhop, дальше VL 12 (severity 3) набирается за секунды + rollback на каждом флаге.
- ФИКС: вести per-tick ground truth (в 20 Гц задаче posHistory — WepAC.java:196-208 — добавлять `groundedAtTick`); освобождать проверку спайка, если игрок был grounded в последние ~150 мс. Системно решается B1.

### A7 🔴 KillAura «Rate» наказывает джиттер/баттерфляй-кликеров
- ГДЕ: `checkRate` (KillAuraCheck.java:249-262): >14 damage-событий/с, buffer 2, severity 3.
- ПРОБЛЕМА: в 1.9+ `EntityDamageByEntityEvent` fires и на слабых ударах с неполным кулдауном. Легитимные 15-20 CPS в бою → флаг каждые ~3 удара → VL 18 (threshold) за ~5 с, кик-стадия 25 за ~8 с непрерывного легитимного джиттер-боя (single-check confirm 18×1.5=27 тоже достижим).
- ФИКС: считать только «значимые» атаки (charge ≥0.4-0.5 из уже собираемого `attackCharges`), либо поднять cap до ~20; правильный сигнал — физически невозможное: ≥13 атак/с С charge ≥0.98 (кулдаун меча ~0.625 с ограничивает честный full-charge rate ~12.5/с). Высокий CPS + низкий charge = честный джиттер, не флагать.

### A8 🟠 CooldownLock FP на PvE-гриндерах и дисциплинированных 1.9+ игроках
- ГДЕ: `checkCooldownLock` (KillAuraCheck.java:150-186); заряды пушатся для ВСЕХ жертв (KillAuraCheck.java:133-136).
- ПРОБЛЕМА: игрок, фармящий мобов с ожиданием полного заряда (оптимальный DPS-паттерн), даёт ровно сигнатуру: 15+ атак, charge≈1.0 (stddev≤0.012), интервалы≈период кулдауна (stddev≤80 мс достижим у ритмичного игрока). Buffer 2 → severity 4 → threshold 18 → кик-путь за минуту фарма. Аналогично `checkCritRhythm` (CriticalsCheck.java:79-113) для игроков, прыгающих перед каждым PvP-ударом (ритм-криты — стандартная техника).
- ФИКС: (1) CooldownLock — только по PvP-жертвам (моб-фарм не вредит); (2) требовать совпадения среднего интервала с точным периодом кулдауна оружия (±10 мс) — бот попадает в период, человек в «реакцию на полоску заряда» (у человека интервал = cooldown + reaction jitter); (3) cross-signal voting: флаг ауры только при 2+ независимых сигналах в окне ~5 с (см. A14).

### A9 🟠 BoatFly: баллистические дуги после трамплинов + мгновенный tempban по умолчанию
- ГДЕ: `BoatFlyCheck.onVehicleMove` (BoatFlyCheck.java:70-145); config `punishments.overrides.BOATFLY at:3 → tempban 1d`.
- ПРОБЛЕМА: guard `vLen2>1.0` сбрасывает streaks только пока лодка быстрая; после ледяного трамплина/пушки скорость падает ниже 1.0, а dy>0.05 на вершине дуги держится 4+ события → rise-флаг → threshold 3 + severity 5 → мгновенный ТЕМПБАН за легитимный трюк. Также: streaks-мапа течёт при выгрузке чанка с лодкой (только предохранитель на 1000); флаг вешается на passengers.get(0) — при 2 пассажирах виноват не обязательно он.
- ФИКС: баллистическая модель для лодки (интегрировать vy c гравитацией/драгом лодки и флагать только расхождение — переиспользовать подход Sim); для rise-сигнала дополнительно требовать низкую горизонтальную скорость (зависание, а не дуга); дефолтное наказание — alert/kick, бан через record-систему за рецидив; чистка streaks по last-seen; атрибуция — контролирующий пассажир.

### A10 🟠 LongJump FP на отскоках от слизи/льда
- ГДЕ: `checkLongJump` (MovementMonitor.java:307-332), `nearSlimeBelow` (808-816) — только 3 блока под текущей позицией.
- ПРОБЛЕМА: высокий отскок от слизи сохраняет горизонтальный импульс >0.55 b/t на всю дугу; в середине дуги слизи рядом уже нет → buffer 2 → флаг. Разгон с льда + слизь — обычный паркур-паттерн.
- ФИКС: таймстемпы `lastSlimeContact/lastIceContact` (ставить при grounded-контакте со слизью/льдом), exempt 2-3 с после; либо флагать только РОСТ горизонтальной скорости в воздухе (в ванили она монотонно падает ~×0.91/тик без импульсов) — это физически строгий критерий.

### A11 🟠 ElytraFly FP на dive→pull-up (обмен энергии)
- ГДЕ: `checkElytraFly` (MovementMonitor.java:361-384): rise>0.08, 5 семплов (1.25 с) без буста → флаг.
- ПРОБЛЕМА: легитимный пилот набирает высоту без фейерверков, вытягивая из пикирования (speed→height); подъём >0.08 b/t дольше 1.25 с — рутина для горных маршрутов и PvP-манёвров.
- ФИКС: гейтить rise-сигнал по горизонтальной скорости (обмен энергии ⇒ hSpeed высока, exempt при hSpeed>~0.8-1.0), либо считать полную механическую энергию E=hSpeed²+vSpeed²+2·g·h и флагать только её РОСТ без буста. Чистый hover-climb (низкая hSpeed + rise) сохраняется как сигнал.

### A12 🟠 MultiTarget FP на sweep-атаках/моб-фермах
- ГДЕ: `checkMultiTarget` (KillAuraCheck.java:471-500): 4+ разные жертвы за 1.5 с, каждая ≤40° от взгляда.
- ПРОБЛЕМА: Sweeping Edge по толпе мобов на ферме легитимно бьёт 4+ целей за один взмах, все около прицела → buffer 2 → severity 3 → кик-путь при sustained-фарме.
- ФИКС: считать только жертв-игроков (мульти-аура по игрокам — вредоносный кейс), ЛИБО исключать связку «меч со Sweeping Edge + все жертвы не-игроки», ЛИБО требовать попадания в РАЗНЫЕ взмахи с ротацией между ними.

### A13 🟠 Geyser/Bedrock-игроки структурно ломают GCD, InventoryMove и ритм-проверки
- ГДЕ: `checkMouseGcd/Yaw` (KillAuraCheck.java:317-362), `InventoryMoveCheck` (весь), pacing/cooldown-lock.
- ПРОБЛЕМА: Bedrock-клиенты (тач/контроллер) не квантуют ротации по мышиному шагу → GCD-коллапс гарантирован; GUI на Bedrock не захватывает камеру так же → InventoryMove-флаги. Любой Geyser-сервер получает поток FP.
- ФИКС: детект Floodgate (presence + `FloodgateApi.isFloodgatePlayer(uuid)` через reflection) → exempt для GCD/InventoryMove/pacing (reach/физика остаются); документировать матрицу совместимости.

### A14 🟠 Независимые флаги KillAura-детекторов вместо голосования сигналов
- ГДЕ: вся `KillAuraCheck` — каждый из 10 детекторов independently добавляет VL в один CheckType.
- ПРОБЛЕМА: у элитных игроков достижимы поодиночке: aim-lock (stddev<0.5°), perfect-hits, cooldown-lock, snap-aim на быстром флике. README предупреждает только про aim-lock/perfect-hits. Отдельные FP-эпизоды суммируются в общий VL KILLAURA и ведут к кику.
- ФИКС: voting-схема: детекторы складывают «подозрения» в короткое окно (5 с), флаг (severity 3-4) выдаётся при 2+ независимых сигналах; одиночные сигналы → severity 1 (информационно для ИИ/стаффа). Дополнительно: сбрасывать GCD-семплы при детекте смены чувствительности мыши (структура квантования изменилась — смешанная история коллапсирует gcd; сейчас риск одного флага после смены sens в бою).

### A15 🟡 SilentRot: FP на интенсивных фликах, FN на yaw-only ротациях
- ГДЕ: `SilentRotCheck.onMove` (SilentRotCheck.java:34-77).
- ПРОБЛЕМА: 5 реверсов pitch ≥30° за 5 с возможны в честном бою (переключение земля/воздух-цели); при этом silent-ротации ТОЛЬКО по yaw не детектируются.
- ФИКС: требовать корреляции с действием: реверс в пределах ~100-150 мс от BlockPlace/attack/use-item (это и есть сигнатура silent-rot); не считать реверсы, заканчивающиеся на реально взаимодействованной цели/блоке. Добавить yaw-реверсы с той же action-гейтовой логикой.

### A16 🟡 Anti-KB (Velocity) — грубая модель
- ГДЕ: `checkVelocityAbsorption` (MovementMonitor.java:181-218), захват КВ в ConnectionListener.onDamage (125-136).
- ПРОБЛЕМА: expected = kbLen×{1.6|2.2} — константы без симуляции трения (0.91/тик в воздухе, 0.6 на земле); `kbActual` включает СОБСТВЕННОЕ движение игрока (спринт-отход → FN), стена/угол на пути КВ → FP; скорость читается на тик позже (уже затухла).
- ФИКС: сохранять вектор КВ; пер-тик интегрировать ожидаемое смещение с драгом; сравнивать проекцию фактического движения НА направление КВ; raycast вдоль КВ — exempt при блокирующем блоке. Системно: часть B1.

### A17 🟡 PacketPhysics Sim: «отмывание» серии импульсов
- ГДЕ: `Sim.onPacket` (PacketPhysics.java:180-193): `err > IMPULSE(1.0)` → re-anchor без заряда.
- ПРОБЛЕМА: чит, поднимающийся на ~1.01 блока/пакет, каждый пакет трактуется как взрыв; после re-anchor базовая скорость завышается, и дальнейший подъём ~0.9/пакет даёт микроскопические err → пакетный слой слепнет. (4 Гц hover-чек подстраховывает, но пакетный слой обязан ловить сам.)
- ФИКС: считать ПОСЛЕДОВАТЕЛЬНЫЕ импульсы: первый — re-anchor, 2+ подряд без grounded/bounce-контекста — заряжать excess. Настоящие взрывы одиночны.

### A18 🟡 Механики 1.21 не покрыты явно: mace (Wind Burst/Density отскок), wind charge, поршни
- ГДЕ: grep по проекту — ноль упоминаний mace/wind_charge; поршневой толчок не порождает PlayerVelocityEvent → `exemptVelocity` не покрывает.
- ПОСЛЕДСТВИЕ: отскок после smash-атаки булавы / запуск Wind Burst могут триггерить AirJump/hover/LongJump; поршневые лифты — коротко зарядить hover/Step (в основном поглощается буферами, но не гарантированно).
- ФИКС: сначала ЭМПИРИЧЕСКИ проверить на живом 1.21.11, какие из событий firing (PlayerVelocityEvent от wind charge/булавы). Затем: exempt-таймер 0.5-1 с при (а) EntityDamageByEntityEvent с MACE у атакующего/жертвы, (б) ProjectileHitEvent WIND_CHARGE рядом с игроком, (в) BlockPistonExtend/RetractEvent, двигающий блок у игрока.

### A19 🟡 Rollback может телепортировать на позицию ДО легитимного телепорта
- ГДЕ: `rollback` (MovementMonitor.java:791-806) использует `lastGroundLocation`; `onTeleport/onRespawn` (ConnectionListener.java:64-83) его не обновляют.
- ПОСЛЕДСТВИЕ: grounded в точке A → /tp в B → чит в B → rollback через полкарты в A (в т.ч. в стену/пустоту по пути).
- ФИКС: в onTeleport/onRespawnставлять `data.lastGroundLocation = event.getTo().clone()` (или null — пропуск rollback до следующего grounded-семпла).

### A20 🟡 `/ac resetvl` — половинчатая реабилитация
- ГДЕ: `ACCommand.resetVl` (ACCommand.java:138-197).
- ПРОБЛЕМА: чистит VL и буферы, но НЕ: cheater-сэмплы игрока в AI-буфере (добавлены при наказании), `aiProbability/aiProbEma`, статус в records.yml (WATCH, 0.6× пороги). FP-кикнутый игрок после «реабилитации» продолжает травить модель и жить под ужесточёнными порогами.
- ФИКС: в resetvl вызывать `ai.purgeCheaterSamplesFrom(uuid)` + сброс `aiProbEma`; лучше — единая команда `/ac rehabilitate <player>` (VL + сэмплы + record + EMA) и документировать её в README как официальный путь отмены FP.

### A21 🟡 Criticals: FN быстрых hop-критов + зависимость от 4 Гц airTicks
- ГДЕ: CriticalsCheck.java:57 (`airTicks >= 5` = 0.25 с на 4 Гц).
- ПРОБЛЕМА: hop-криты (прыжок→удар быстрее 0.25 с) не попадают в packet-ground-spoof ветку; серверная правда о «в воздухе» отстаёт от пакетов.
- ФИКС: per-tick ground truth (B1/кэш из A1); до тех пор — полагаться на crit-rhythm и PacketPhysics, понизить ожидание от packet-ветки.

## B. Архитектурный потолок (что отделяет от Grim-класса)

### B1 🔴 Нет попакетно-тиковое детерминированной симуляции движения
- ГДЕ: архитектура: `MovementMonitor` (4 Гц окна) + `PacketPhysics` (вертикаль, wall-clock).
- ПРОБЛЕМЫ:
  1. Горизонталь НЕ симулируется: константные лимиты (0.29×1.45 и т.п.) вместо модели трение/ускорение/коллизии → тонкие speed/strafe-читы под лимитом живут вечно, а список exempt-ов (лёд, слизь, soul speed, swift sneak, потоки воды…) бесконечно растёт.
  2. Нет коллизионной симуляции: Phase — только центральная колонна и только occluding-блоки (стекло/листва — FN); step-up/sneak-edge/выталкивание не моделируются.
  3. Нет тиковой атрибуции пакетов: Sim считает шаги как round(dt/50) по wall-clock; server-ground-truth берётся один раз на тик для всей очереди (PacketPhysics.java:272) → рассинхрон на границах приземления/взлёта в обе стороны.
  4. Нет транзакций: без outbound PING/pong невозможно точно знать, что клиент видел при отправке пакета → лаг-компенсация эвристическая (пинг-окна) вместо точной.
  5. Окна 4 Гц усредняют микронарушения: 2 тика чита + 3 тика легитимно в одном окне = невидимо.
- ФИКС (поэтапно):
  1. Расширить duplex-хендлер перехватом `write()` (см. B2), начать слать `ClientboundPingPacket` (reflection, кэш конструктора) с фиксированным шагом; по входящим pong строить точную карту «пакет → тик клиента» (Grim-подход).
  2. `MovementSim` на игрока: ванильная физика за тик (gravity 0.08/drag 0.98, jump 0.42+0.1×boost, ground friction 0.6 + input accel, air control, step-up 0.6, sneak-edge, коллизии с кэшем BB блоков чанка на тик, ice/slime friction, жидкости, climbables, уравнения элитры) → предсказанная позиция vs заявленная → аккумулировать offset по осям → флаг при offset>ε (0.03-0.1) N тиков подряд.
  3. Ground truth — из предсказания (а не block-raycast): исчезает весь класс A1.
  Это месяцы работы, но это ЕДИНСТВЕННЫЙ путь к 10/10 детекта. Прагматичный промежуточный шаг: PacketEvents как soft-depend + горизонтальная проверка монотонности (в воздухе hSpeed может только падать ×~0.91/тик без velocity-событий).

### B2 🟠 Пакетный слой read-only
- ГДЕ: `PacketSniffer` переопределяет только `channelRead`.
- ПОСЛЕДСТВИЕ: невозможны транзакции (нужен write), пакетные setbacks (Grim-стиль, дешевле и точнее Bukkit-телепорта), перехват/анализ исходящих.
- ФИКС: переопределить `write()` в том же хендлере (наблюдение исходящих безопасно; для транзакций — конструирование ping-пакета через reflection).

### B3 🟠 Семья BadPackets минимальна
- ГДЕ: `PacketSniffer.evaluate` (357-365): только pitch>90.5 и NaN-координаты.
- ОТСУТСТВУЮТ: невозможные дельты ротации за пакет (>180°/50 мс), дубли flying-пакетов в одном клиентском тике, действия после смерти/в транспорте, order-нарушения 1.9+ (attack до rotation в одном тике — сигнатура части аур), несколько USE_ITEM/USE_ITEM_ON за тик, клики инвентаря мёртвым, place/break с несогласованной ротацией (silent-place без реверса — см. A15).
- ФИКС: после B1/B2 реализовать порядок/порядочность проверки (аналог Grim BadPackets A-P). Они дёшевы и при верной спеке почти детерминированы (нулевой FP) — лучшие источники VL.

### B4 🟡 Reach измеряется в момент события, а не в момент пакета атаки
- ГДЕ: `ReachCheck.onAttack` (ReachCheck.java:36-79): `attacker.getEyeLocation()` на MONITOR.
- ПРОБЛЕМА: к моменту события сервер мог применить более поздние ротации из той же пачки пакетов; жертва лаг-компенсируется, атакующий — нет. Плюс плоский бонус +0.35 при velocity>0.1 (ReachCheck.java:49) слишком щедр (эффективный лимит до ~3.4-3.75 на пинге).
- ФИКС: брать eye-позицию/ротацию из самого USE_ENTITY-пакета (очередь пакетного слоя, атрибуция по тикам из B1); бонус velocity — пропорционально компоненте скорости вдоль направления удара, кап ≤0.25.

### B5 🟡 Timer: граница 1.05× и полное исключение высокого пинга
- ГДЕ: `PacketSniffer.evaluate` (316-333), config `timer-max-rate: 21`.
- ПРОБЛЕМА: 20×1.05=21.0, условие `rate > 21` → 1.05× НЕ ловится (комментарий в конфиге обещает обратное); игроки с ping>450 исключены полностью (чит на плохом соединении неуязвим); гранулярность окон 1 с.
- ФИКС: дефолт 20.5 (или `>=`); долго: транзакционный таймер (подсчёт клиентских тиков между парами ping/pong — ловит 1.001× и не боится пинга).

### B6 🟡 Blink: фиксированный 2 с таймаут
- ГДЕ: PacketSniffer.java:338-354.
- ПРОБЛЕМА: блинки 0.5-1.5 с невидимы; pos-jump>16 блоков флагуется типом BLINK (косметика — семантика BADPACKETS/PACKETFLY).
- ФИКС: коррелировать длину гэпа с набранным за него смещением (телепорт-размерное перемещение при малом гэпе = blink-сигнатура), а не только длительность.

## C. ИИ-подсистема

### C1 🟠 Одноклассные раунды обучения
- ГДЕ: `AIBrain.trainRound` (AIBrain.java:376-378).
- ПРОБЛЕМА: если в буфере только один класс (например, после рейда много cheater-сэмплов, legit не накоплен), батч становится одноклассным → градиент двигает ВСЕ вероятности в одну сторону → шторм FP-алертов и ужесточение порогов у честных.
- ФИКС: пропускать раунд при отсутствии класса; кап соотношения классов в батче (≤70/30); логировать состав раунда.

### C2 🟠 Нормализатор отравляется читерами и AFK
- ГДЕ: `AIBrain.observe` (197-208) — вызывается для КАЖДОГО скоринга.
- ПРОБЛЕМА: популяционные mean/std включают телеметрию читеров (норма сдвигается к читам — следующие читы выглядят нормальнее) и AFK-нули (норма сдвигается к нулям). Freeze на 250k наблюдений консервирует смещение.
- ФИКС: не observe-ить игроков с totalVl>0, aiProbability>~0.5, около-нулевой активностью; либо робастные статистики (running median + MAD вместо mean/std).

### C3 🟠 Clean-play лейблы: AFK ≠ активная честная игра
- ГДЕ: `checkCleanPlay` (343-355): 20 минут ОНЛАЙНА с VL 0 → 3 legit-сэмпла.
- ФИКС: гейт по активности (пройденное расстояние/взаимодействия в окне); не донатить почти-нулевые векторы; приоритет — CombatProfiler-донорство (оно уже с гейтами качества).

### C4 🟠 Инженерия признаков
- ГДЕ: `buildRawFeatures` (92-151).
- ПРОБЛЕМЫ: (а) fabricated-дефолты для не-комбата (hitAngle=4.0°, charge=0.85) — модель не отличает «не дрался» от «дрался вот так»; (б) признаки зависят от включённости ДРУГИХ проверок: f[16] заполняет только CriticalsCheck (CriticalsCheck.java:74), f[17] — только SilentRotCheck (SilentRotCheck.java:50); отключение проверки молча меняет распределение входов при замороженном нормализаторе → коррупция модели; (в) ping как признак (f[13]) учит сервер-специфичным корреляциям; (г) 3-секундные агрегаты теряют временну́ю структуру (бот, чередующий легитимные и читерские секунды, усредняется в «легитимного»).
- ФИКС: явные бинарные `hasCombat/hasMovement` + нули вместо выдуманных значений; сбор телеметрии ВЫНЕСТИ из проверок в постоянно включённые коллекторы (флаги и признаки развязать); рассмотреть отказ от ping-признака; средне-срочно — секвенционная модель по покадровым (1 с) векторам или градиентный бустинг по дельта-признакам между кадрами.

### C5 🟡 Математика обучения
- ГДЕ: `NeuralNetwork.train` (86-122): MSE-дельта `err·out·(1-out)` на сигмоиде → затухание градиента в насыщении (а лейблы как раз насыщают); lr фиксирован, нет momentum/weight decay/валидации; `lastAvgError` — только train error.
- ФИКС: binary cross-entropy (дельта = out − target), momentum 0.9, L2 ~1e-4, holdout 10% буфера с AUC в логе каждого раунда, расписание lr по trainSteps.

### C6 🟡 Предобученная модель дрейфует без якорей
- ГДЕ: буфер стартует пустым (pretrained/ содержит только веса); онлайн-SGD на живых данных постепенно перезаписывает знания архетипов (catastrophic forgetting).
- ФИКС: включить архетипы PreTrainer в постоянный anchor-набор и подмешивать 20-30% в каждый раунд.

### C7 🟡 Адаптивность ослабляет защиту для «неизвестных»
- ГДЕ: `adaptiveMultiplier` (241-249), `Check.threshold` (Check.java:37-44).
- ПРОБЛЕМА: aiProbEma≈0 → пороги ×1.30 — первому тонкому читу даётся +30% запаса; гейт `profile.count()>=20` сбрасывается каждую сессию (профили не персистятся, см. C8).
- ФИКС: потолок релаксации 1.10-1.15 (пол 0.5× оставить); персистить профили.

### C8 ⚪ Мёртвый код / пробелы персистентности ИИ
- ГДЕ: `PlayerProfile.save/load` (PlayerProfile.java:52-72) — НИКОГДА не вызываются (проверено grep): выученный профиль игрока умирает при выходе; `AIBrain.sync()` (574-576), `FeatureVector.copyOf` (46-52), `SilentRotCheck.reversalRate` (80-84) — не используются.
- ФИКС: персистить профили (ai/profiles.bin или внутри vl.yml) ИЛИ удалить save/load; удалить мёртвые методы.

### C9 🟡 CombatProfiler: микро-утечки и требование онлайна
- ГДЕ: `lastDonation`/`sessions` (CombatProfiler.java:52-53) не чистятся на quit; `consider()` (124) требует онлайна через 10 с после боя — вышедший сразу после PvP донор теряется.
- ФИКС: чистка в ConnectionListener.onQuit; донорство по сохранённому снапшоту без требования онлайна.

### C10 ⚪ `/ac label` сэмплирует текущие 3 секунды
- ГДЕ: `AIBrain.labelByStaff` (331-340).
- ПРОБЛЕМА: стафф лейблит «cheater» после наблюдения боя, а игрок в этот момент стоит на месте → в буфер уходит почти-нулевой вектор с меткой чита, противоречащий AFK-векторам честных.
- ФИКС: хранить последние N покадровых фич с флагом активности; для label брать самый активный кадр за последние 60 с, либо фичи, сохранённые в момент последнего алерта.

## D. Наказания / учёт / команды

### D1 🟠 `isHarsh()` — хардкодный список глаголов
- ГДЕ: PunishmentManager.java:102-106 (kick/ban/tempban/ban-ip/banip/tkb).
- ПРОБЛЕМА: нестандартные команды наказаний («vban», «punish», «sanction», кастомные алиасы CMI/LiteBans-сборки) НЕ считаются harsh → исполняются БЕЗ confirm-gate → неподтверждённые авто-наказания.
- ФИКС: конфигурируемый `confirm.harsh-commands: [...]`; неизвестные глаголы по умолчанию считать harsh (консервативно), с whitelist «безопасных» (broadcast/warn-команды).

### D2 🟡 Учёт (records) бессрочен
- ГДЕ: RecordManager — WATCH/WANTED без истечения; один FP-кик = вечные 0.6× пороги + объявления при каждом входе.
- ФИКС: авто-даунгрейд WATCH→CLEAN после N дней без страйков (`record.expire-days`, дефолт 30), история в notes сохраняется; WANTED — только ручное снятие (ок).

### D3 🟡 Нет per-world отключений проверок
- ГДЕ: только permission `wepac.bypass` (глобально на игрока).
- ПРОБЛЕМА: мини-игры/паркур-миры/ивенты требуют отключать Fly/Speed/Jesus по МИРУ, а не выдавать bypass игрокам.
- ФИКС: `checks.<type>.disabled-worlds: [...]` + `disabled-regions` (WorldGuard hook, опционально).

### D4 ⚪ `/ac info` только для онлайн; `/ac reload` не перечитывает интервалы задач
- ГДЕ: ACCommand.info (80-84); WepAC.startTasks (194-264) — интервалы decay/score/train фиксируются при включении.
- ФИКС: info — fallback на ViolationStore/records по offline-UUID; reload — перерегистрация таймеров или явная пометка в доках «интервалы требуют рестарта».

### D5 ⚪ QoL стафф-инструментов
- Алерты не содержат координат/мира (стафф не может телепортироваться разобрать FP) — добавить {world} {x} {y} {z} в дефолтный формат; нет пер-чек фильтра алертов у стаффа; toggle `/ac alerts` не переживает рестарт; нет verbose-режима проверок (live-буферы) и dump/paste отчёта для разбора FP (у Grim это ключевой инструмент поддержки).

## E. Совместимость

### E1 🟠 Версионная позиция не объявлена fail-fast

- ФИКС: при включении проверять версию сервера и логировать SEVERE + отключаться, если < 1.21; в README заявить «1.21.x only» (или сделать мульти-версионную модульную структуру — дорого, вероятно не нужно).

### E2 🟠 ViaVersion/Geyser не учитываются

- ФИКС: читать protocol version игрока (ViaVersion API soft-depend, или из handshake через пакетный слой) → гейтить 1.9+-специфичные проверки (cooldown-lock, perfect-hits, charge-признаки ИИ) для legacy-протоколов; Floodgate-exempt по A13.

### E3 🟡 Folia не поддерживается (глобальные шедулеры + main-thread модель)
- ФИКС: как минимум не грузиться на Folia с понятным сообщением (`folia-supported: false` в plugin.yml уже подразумевается); порт — отдельный проект.

### E4 🟡 Сети (Bungee/Velocity): файлы локальны
- ГДЕ: vl.yml/records.yml/model.bin — на сервер.
- ПРОБЛЕМА: читер кикнут на survival-1 → заходит на survival-2 чистым (VL/учёт не разделяются).
- ФИКС (опциональный уровень): MySQL/Redis-бэкенд для VL/records (+plugin messaging синк), модель — общая с версионированием или per-server.

### E5 ⚪ Алиас `/ac` конфликтует с другими плагинами античитов — задокументировать; softdepend-секция в plugin.yml отсутствует (Via/Floodgate/PacketEvents — добавить как softdepend для корректного порядка загрузки).

## G. Тестирование и валидация — главный путь к доверию «10/10»

### G1 🔴 Нет валидации на реальных данных (RESULTS.md сам это признаёт)
- ПРОБЛЕМА: все проценты детекта — один генератор против себя. Без реального корпуса ни одна правка порогов не измерима.
- ФИКС (конвейер):
  1. Рекордер: кольцевой буфер на игрока (фич-кадры, пакетные события, флаги) + `/ac dump <player> [сек]` → анонимизированный CSV/JSON.
  2. Replay-харнесс вне сервера: прогон записанных сессий через чистую логику (Sim, пороги, голосование) — как SelfTest, но на живых данных.
  3. Корпус-фикстуры: записать сессии реальных чит-клиентов (коллекция исходников уже есть — прогнать их на тестовом сервере) И легитимные сценарии: bhop, crit-спам, drag-click, Geyser, swift sneak, mace, элитра-маршруты, WorldGuard-зоны, лобби-толпа (A1), слизь-паркур (A10), фермы со sweep (A12).
